# Task 013: 연동 예외 처리 및 안정화

## 목표

노션 호출의 타임아웃, 재시도, 요청 제한, 로그 정책을 정리한다. 재시도는 SDK 옵션(`maxRetries`)으로만 처리하고 직접 재시도 루프를 만들지 않는다. 429 최종 실패는 요청 제한 안내를, 그 밖의 연동 실패는 연동 오류 화면을 보여준다.

## 변경 파일

| 파일                                    | 상태 | 내용                                                                                           |
| --------------------------------------- | ---- | ---------------------------------------------------------------------------------------------- |
| `src/lib/notion/client.ts`              | 수정 | SDK에 Node http(s) 기반 `fetch`를 넘겨 재시도가 실제로 노션에 나가도록 함 (아래 "발견한 문제") |
| `src/lib/notion/get-published-quote.ts` | 기존 | 429 최종 실패는 `rateLimited`, 그 밖의 실패는 `unavailable`로 분류 (Task 011에서 구현)         |

## 설계 결정

- 타임아웃 10초 (`NOTION_TIMEOUT_MS`), 재시도 2회 (`NOTION_MAX_RETRIES`). SDK 재시도는 429와 529를 항상 재시도하고, 500·503은 GET과 DELETE만 재시도한다. 타임아웃은 SDK가 재시도하지 않는다.
- 연속 실패 임계치는 별도 서킷 브레이커를 만들지 않고, 재시도 횟수 상한(2회)을 임계치로 본다.
- 장애 재현은 운영 코드에 테스트 경로를 넣지 않고 로컬 프록시로 했다. 기존 테스트 전용 설정 `NOTION_BASE_URL`로 노션 주소를 프록시에 연결하고, 프록시가 실제 노션에 전달하되 모드에 따라 타임아웃, 429, 503을 끼워 넣었다. 프록시 코드는 프로젝트 밖(scratchpad)에 있고 저장소에 들어가지 않는다.

## 발견한 문제 (수정함)

- **재시도가 노션에 나가지 않던 문제**: Next.js는 같은 요청 안에서 GET fetch를 묶어 재사용한다(`dedupe-fetch`). SDK가 Next의 fetch를 그대로 쓰면, 재시도가 같은 실패 응답을 받고 실제 노션 호출은 1회뿐이었다. 캐시 옵션(`cache: 'no-store'`)으로는 막히지 않았다. 그래서 SDK에 Node http(s) 기반 `notionFetch`를 넘겨 해결했다. 수정 전에는 429와 503 시나리오가 1회 호출로 끝났고, 수정 후에는 3회 호출된다.

## 확인 중 발견한 사항

- 개발 서버에서 연동 오류 응답은 HTTP 500으로 나간다. 연동 오류 화면이 보이는 것은 맞지만, 상태 코드는 운영에서도 500이다.
- 브라우저 콘솔에는 개발 모드에서만 React가 출력하는 오류 스택이 찍힌다. 운영 빌드에서는 나오지 않는다. 서버 로그 코드는 `service_unavailable`, `notionhq_client_request_timeout`, `rate_limited` 등 오류 코드만 남는다.
