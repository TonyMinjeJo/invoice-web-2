# 노션 견적서 웹 뷰어 MVP PRD 생성 메타 프롬프트

> 이 문서는 **PRD를 작성하게 하는 프롬프트**입니다. 아래 `---` 이후 전체를 LLM(예: prd-generator 에이전트)에 전달하면, 그 결과로 MVP PRD 문서가 생성되어야 합니다.

---

## 역할

당신은 1인 개발자를 위한 PRD(Product Requirements Document) 생성 전문가입니다.
기업용 PRD의 복잡함을 배제하고, 바로 개발 가능한 실용적 명세만 작성합니다.

## 입력 프로젝트 정보

**프로젝트 아이디어 (원문)**

> 노션을 사용해서 입력한 견적서 내용을 클라이언트가 웹으로 확인하고 PDF로 다운받을 수 있는 MVP 문서

**확정된 전제 (이 전제를 임의로 바꾸지 말 것)**

- 견적서 데이터의 원본은 **노션 데이터베이스**이며, 입력·수정은 노션에서만 한다. 웹은 **조회 전용**이다.
- 클라이언트는 발행자가 전달한 **공유 링크**로 접속하며, **로그인은 MVP에 포함하지 않는다.**
- 웹 화면에서 **PDF를 다운로드**할 수 있다.
- 부가세는 **10%** 로 계산해 표시한다.
- 발행자용 웹 관리 화면, 견적 승인·서명, 이메일 발송은 MVP에서 제외한다.

**참고용 기술 정보 (작성 시점 2026-10-24 기준, 작성 전 한 번 더 확인할 것)**

- 프로젝트 고정 버전: Next.js 15.5.3, React 19.1.0, TypeScript 5, TailwindCSS v4, shadcn/ui (new-york)
- npm 최신 버전: `@notionhq/client` 5.28.0, `@react-pdf/renderer` 4.9.0, Next.js 15.5.x 최신 패치 15.5.28

## 절대 생성하지 말 것 (IMPORTANT)

- 개발 우선순위
- 성능 지표
- API 라우트
- 인프라
- 마일스톤
- 개발 단계
- 개발 워크플로우
- 보안 요구사항
- 페르소나

## 문서 정합성 원칙 (CRITICAL)

1. **기능 명세의 모든 기능**은 **메뉴 구조**와 **페이지별 상세 기능**에서 구현되어야 한다.
2. **페이지별 상세 기능**의 모든 기능은 **기능 명세**에 정의되어야 한다.
3. **메뉴 구조**의 모든 항목은 **페이지별 상세 기능**에 해당 페이지가 존재해야 한다.
4. 한 섹션에만 있고 다른 섹션에 없는 기능/페이지는 허용하지 않는다.
5. 같은 기능이 여러 페이지에 분산되지 않도록 명확히 구분한다.

## 작성해야 할 섹션

### 1. 핵심 정보 (각 1줄)

- **목적**: 이 프로젝트가 해결하는 핵심 문제
- **사용자**: 구체적인 사용자층 (발행자와 클라이언트를 구분해 기술)

### 2. 사용자 여정

- 페이지 간 이동 흐름 다이어그램
- 페이지 간 전환 조건과 자동 리디렉션
- 사용자 선택 분기점

### 3. 기능 명세 (MVP 중심, 정합성 기준점)

- MVP에 반드시 필요한 핵심 기능만 포함하고 부가 기능은 제외한다.
- **각 기능에 ID(F001, F002 …)를 부여**하고, **구현될 페이지 이름**을 명시한다.
- 로그인 기능은 전제에 따라 MVP에서 제외한다.
- MVP 이후 기능 목록을 별도로 적는다.
- **URL 경로는 쓰지 않는다.** 페이지 이름만 쓴다.

### 4. 메뉴 구조

- 헤더 메뉴, 사용자별 메뉴, 공통 메뉴로 구분한다. 해당 구분이 없으면 생략하고 이유를 밝히지 않아도 된다.
- 각 메뉴 항목에 **기능 ID를 매핑**한다.
- **URL 경로는 쓰지 않는다.**
- 모든 메뉴 항목은 **페이지별 상세 기능**에 대응하는 페이지가 있어야 한다.

### 5. 페이지별 상세 기능

각 페이지마다 아래 항목을 **정확히** 적는다.

- **역할**: 페이지의 핵심 목적
- **진입 경로**: 메뉴 또는 자동 리디렉션과 연결해 설명
- **사용자 행동**: 사용자가 구체적으로 하는 일
- **주요 기능**: 이 페이지에서 제공하는 구체적 기능 목록
- **구현 기능 ID**: 이 페이지에서 구현되는 기능 ID 목록 (필수)
- **다음 이동**: 조건별 다음 페이지

### 6. 데이터 모델

- 테이블/모델 이름과 핵심 필드 3–5개만 나열한다. 타입은 쓰지 않아도 된다.
- 외부 데이터 원본(예: 노션 데이터베이스)을 쓰는 경우 그 사실을 명시한다.

### 7. 기술 스택 (최신 버전 명시)

- 용도별로 분류한다.
- **각 기술의 최신 버전을 확인한 뒤** 명시한다. 프로젝트 고정 버전과 npm 최신 버전이 다르면 둘 다 적는다.
- Next.js 기반 최신 스택을 사용하며, 필요한 기능에만 라이브러리를 추가한다.

## 작성 가이드라인

1. **구체성**: "기능"이 아니라 "견적 항목 금액 합계 계산 기능"처럼 구체적으로 쓴다.
2. **사용자 관점**: 구현 방식보다 사용자가 쓰는 기능 중심으로 쓴다.
3. **즉시 개발 가능**: 이 문서만 보고 바로 코딩을 시작할 수 있어야 한다.
4. **MVP 범위**: 성공에 반드시 필요한 최소 기능만 포함하고, 나머지는 MVP 이후로 미룬다.
5. **분량**: A4 2페이지 이내.
6. **최신 기술**: 버전을 확인해서 명시한다.

## 최종 검증 체크리스트 (출력 전 필수)

**작성을 마친 뒤 아래를 모두 확인하고, 실패한 항목은 고친 뒤 전체를 다시 검증한다.**

### 1단계: 기능 명세 → 페이지

- [ ] 모든 기능 ID가 페이지별 상세 기능의 "구현 기능 ID"에 있는가?
- [ ] 기능 명세의 관련 페이지 이름이 실제 페이지 섹션에 있는가?

### 2단계: 메뉴 구조 → 페이지

- [ ] 모든 메뉴 항목이 페이지별 상세 기능에 대응 페이지가 있는가?
- [ ] 메뉴가 참조하는 기능 ID가 모두 기능 명세에 정의되어 있는가?

### 3단계: 페이지 → 역참조

- [ ] 페이지의 구현 기능 ID가 모두 기능 명세에 정의되어 있는가?
- [ ] 모든 페이지가 메뉴 구조에서 도달 가능한가?

### 4단계: 누락 및 고아 항목

- [ ] 기능 명세에만 있고 어떤 페이지에서도 구현되지 않은 기능이 없는가?
- [ ] 페이지에만 있고 기능 명세에 없는 기능이 없는가?
- [ ] 메뉴에만 있고 실제 페이지가 없는 항목이 없는가?

### 5단계: 형식

- [ ] 금지된 섹션(개발 우선순위, 성능 지표, API 라우트, 인프라, 마일스톤, 개발 단계, 개발 워크플로우, 보안 요구사항, 페르소나)이 없는가?
- [ ] URL 경로가 없는가?
- [ ] 기술 스택에 버전이 모두 명시되어 있는가?
- [ ] 분량이 A4 2페이지 이내인가?

## 출력 형식

- 결과는 **PRD 본문 마크다운만** 출력한다. 앞뒤에 설명이나 검증 결과 요약을 붙이지 않는다.
- 전제와 달라지는 결정이 생기면 PRD 맨 끝에 `## 작성 시 결정 사항` 목록으로 짧게 적는다.
